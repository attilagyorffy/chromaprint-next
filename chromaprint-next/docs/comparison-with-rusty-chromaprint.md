# Comparison with rusty-chromaprint

[rusty-chromaprint](https://github.com/darksv/rusty-chromaprint) is an independent pure-Rust port of the C Chromaprint library by darksv. This document summarises how it compares to chromaprint-next and where it falls short of the C reference implementation.

## Test methodology

The `chromaprint-test-suite` crate runs all three implementations (C, chromaprint-next, rusty-chromaprint) against identical PCM inputs and compares raw fingerprints (`Vec<u32>`), compressed binary encodings, and — where the API supports it — base64-encoded strings and SimHash values. Tests cover mono and stereo audio at multiple sample rates (8000, 11025, 44100 Hz), silence, and all five algorithm variants.

chromaprint-next produces bit-identical output to the C library across all algorithms and all test inputs. rusty-chromaprint matches for the most common case (Test2 with properly-declared audio) but diverges in several areas detailed below.

## Resampler differences

The C library bundles FFmpeg's `av_resample` — a polyphase FIR resampler with a Kaiser-windowed sinc filter. chromaprint-next contains a direct Rust translation of this code, reproducing its fixed-point i16 arithmetic and filter bank construction exactly. rusty-chromaprint instead uses the [`rubato`](https://crates.io/crates/rubato) crate, a general-purpose async resampler with a different filter design.

For typical audio inputs (mono or stereo with correctly-declared channel counts), the two resamplers produce sufficiently similar output that the downstream fingerprint is identical. However, when processing longer streams — such as the `test_stereo_44100.raw` file fed as a single mono channel (172,800 samples instead of 86,400) — small numerical differences accumulate through the resampler and propagate to a few differing sub-fingerprint bits. The fingerprint lengths remain identical and most sub-fingerprints match, but strict bitwise equality is not guaranteed for all inputs.

chromaprint-next avoids this issue entirely by using the same resampling algorithm as the C library.

## Algorithm preset issues

### Test3: wrong frame overlap

The C library has a [known bug](known-bugs.md) where Test3's constructor omits the `set_frame_overlap()` call, leaving the overlap at 0 instead of the intended 2731. chromaprint-next deliberately reproduces this bug for database compatibility.

rusty-chromaprint's `preset_test3()` sets `frame_overlap` to `DEFAULT_FRAME_OVERLAP` (2731) — the mathematically correct value, but not what the C library actually does. This means Test3 fingerprints from rusty-chromaprint are incompatible with fingerprints generated by the C library or chromaprint-next.

### Test4 and Test5: incomplete presets

rusty-chromaprint's `preset_test4()` and `preset_test5()` are missing classifier and filter coefficient configuration:

- `preset_test4()` only calls `.with_id(3).with_removed_silence(50)` — no classifiers or chroma filter coefficients are set, so the classifier list is empty and the fingerprint calculator produces no sub-fingerprints.
- `preset_test5()` only calls `.with_id(4).with_frame_size(...).with_frame_overlap(...)` — same problem.

Both presets produce empty fingerprints. In chromaprint-next, all five presets are fully configured with the correct classifiers and coefficients matching the C library.

rusty-chromaprint includes a fingerprint matching API (`match_fingerprints`) that chromaprint-next does not currently provide. chromaprint-next provides encoding, decoding, and hashing functions that rusty-chromaprint lacks.

## Performance

chromaprint-next is approximately **4x faster** than rusty-chromaprint across all input sizes. Both are pure Rust, but differ significantly in their internal architecture.

| Duration | chromaprint-next | rusty-chromaprint | Speedup |
|----------|-----------------|-------------------|---------|
| 2 sec | 0.32 ms | 1.33 ms | 4.1x |
| 10 sec | 0.76 ms | 3.20 ms | 4.2x |
| 30 sec | 2.24 ms | 9.57 ms | 4.3x |
| 60 sec | 4.43 ms | 19.07 ms | 4.3x |
| 120 sec | 8.88 ms | 37.91 ms | 4.3x |

Measured on Apple M1 Max, macOS 26.6, Rust 1.96.0, using the Test2 (default) algorithm on mono 44100 Hz input. See [benchmarks.md](benchmarks.md) for full results including comparison with the C reference.

### Why chromaprint-next is faster

The performance gap comes from these areas:

**Resampler.** The largest difference is in the 44100→11025 Hz resampling stage, still the largest stage at ~40% of chromaprint-next's time. chromaprint-next ports the C library's `av_resample` — a polyphase FIR filter with fixed-point i16 arithmetic and an 80-tap Kaiser-windowed sinc kernel. The inner convolution loop is accelerated with NEON SIMD intrinsics on aarch64 (`smlal`/`smlal2` with eight accumulator chains, four outputs per pass, and one shared filter load at integer rate ratios such as 44.1 kHz) and SSE2 on x86_64 (`_mm_madd_epi16`). Filter banks are built once per process and shared between streams. rusty-chromaprint uses [`rubato`](https://crates.io/crates/rubato), a general-purpose asynchronous resampler designed for arbitrary rate conversion. rubato operates in f64, supports variable ratios, and has higher per-sample overhead — capabilities that are unnecessary for chromaprint's fixed 4:1 downsampling.

**FFT processor.** chromaprint-next's FFT processor uses a power-of-2 ring buffer with bitmask indexing (instead of modulo), bulk `copy_from_slice` for input, and a fast path that avoids per-element index masking when the frame doesn't wrap around the buffer. Frames that do wrap are windowed as two contiguous SIMD calls. The real FFT's twiddle pass is fused with the power spectrum in one NEON loop.

**Chroma extraction.** Consecutive bins that map to the same note are summed in a register instead of through memory.

**Bounds-check elimination.** In the resampler's hot path, where surrounding guards already prove the access is in-bounds, `get_unchecked` is used to eliminate redundant bounds checks that the compiler cannot otherwise remove.

All of these optimisations produce bit-identical output to the C reference — they only affect how fast the computation runs, not what it computes.

## Conclusion

For the default Test2 algorithm with properly-declared audio streams, rusty-chromaprint produces identical fingerprints to the C library and is a viable alternative. However, chromaprint-next is a closer match to the C reference implementation:

- **Bit-identical output** across all five algorithm variants, all sample rates, and all channel configurations — including edge cases.
- **Bug-compatible** with the C library's Test3 quirks, ensuring database compatibility with existing C-generated fingerprints.
- **Complete presets** for all algorithms, not just Test1 and Test2.
- **Same resampling algorithm** as the C library, eliminating numerical divergence from third-party resamplers.
- **~4x faster** than rusty-chromaprint and ~2x faster than the C reference, thanks to SIMD kernels and hot-path work that is verified bit-exact.
